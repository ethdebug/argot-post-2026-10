soldb-wasm in the browser

This page runs soldb, Walnut's Solidity debugger, compiled to WebAssembly, in this browser tab. It steps through a real transaction offline, from saved files, and highlights the source range of each EVM step. Debugging by soldb (WebAssembly); the page only displays what soldb reports. Use the step buttons, the keys, the slider, or click a source line to run to it.

Part of the ethdebug post appendix, with Storage, by name and ethdebug in depth.

The same debugger and the same page code step through a different language, because both compilers write ethdebug.

Shop.place: a saved trace of a real transaction (10 MB, 3,736 EVM steps), with solc's ethdebug output (Walnut's solc, walnuthq/solidity PR #10). soldb parses the trace (Trace.fromJson), reads solc's ethdebug (attachEthdebug), maps each step to its source (step(i)) and reads the contract's state (state(i)).

soldb, a Solidity debugger, stepping through a Fe contract, using only Fe's ethdebug output. Debugging by soldb (WebAssembly); the page adapts only the file layout, listed below.

Tally.Add{n: 4} (tally.fe): a loop, an internal call to weight and a branch, compiled by Fe 26.4.1 at -O 0. The transaction ran on a local anvil node; the page loads the node's saved responses with soldb's Trace.fromTransaction, then attachEthdebug and step(i), the same calls and the same viewer as the Solidity tab.

This tab uses ethdebug's own reference debugger, not soldb; soldb tracks what solc emits today.

BUG is ethdebug's teaching language; its compiler emits the fullest debug data today, a preview of what real-language debugging can show.

Tally (tally.bug), compiled by bugc at optimization level 2. The loop calls weight: a real call, which bugc marks with invoke and return contexts. In weight, the optimizer inlines dbl: those instructions carry transform: ["inline"] and keep the span of the call dbl(i) next to the span of the body x + x.

Step through it in ethdebug's reference trace viewer (ethdebug's reference viewer, not soldb): press Try it on an example, paste the program below into the editor, choose O2 and press Compile & Run. The call stack shows weight(i: 0, n: 4), then weight(i: 0, n: 4) › dbl() marked inline (no call; the body is spliced in).

State from ethdebug alone: solc's pointers for storage, the
    deployed code for immutables; no storage layout.

    

    
A trace holds only the storage a transaction reads
    or writes, so a value shows as unknown until the transaction reads or
    writes it, and stays unknown if it never does.

  

  
The page computes these steps from two fields that
  soldb reports per step: the source span and the EVM call depth.
  "into" goes to the next new span; "over" to the next new span at the
  same or a lower depth; "out" to the first span after the depth drops.
  The EVM depth does not count internal function calls, and every step
  in these transactions is at depth 1, so "over" and "out" are
  disabled here. soldb's own step over and out
  (soldb-debugger) follow internal calls; its WebAssembly
  build does not expose them yet.







What the page adapts (file layout only):


    
  
  • program: Fe's file holds two programs in a Fe-specific
    programs list; the page passes the runtime one
    (environment: "call").
    • 
  
  • sources: Fe lists its sources without their text. The
    page supplies it: tally.fe, and 7 standard-library files
    (builtin-core:/…, builtin-std:/…) copied
    from the Fe repository at tag v26.4.1. Their blake3 hashes match the
    ones in Fe's file.
    • 
  
  • metadata: Fe's whole file, unchanged. soldb reads the
    source ids and paths from its compilation; it needs no
    types or pointers, so none are added. name is the
    program's contract name.
    • 



Display only: Fe has no grammar in Shiki, so the code
is coloured as Rust. soldb reports byte offsets; the page converts them
to string positions to draw the span (one std file has non-ASCII text).
File names are shown without their directory. soldb reports no function
names for Fe (its function detection targets Solidity) and no variables
(Fe emits none).
