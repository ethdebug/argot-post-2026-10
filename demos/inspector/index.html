Storage, by name

One contract, Scores, in a few scenes. Click a byte in a word of storage, and the variable that owns it lights up; click a variable, and its bytes light up. "How this was found" shows each step from the variable to its bytes. Some scenes compare two points (Before | After) and mark what changed.

Decoded by ethdebug's reference library from solc's ethdebug output (a preview build of Walnut's solc fork, walnuthq/solidity PR #10). Each variable's base slot, offset and type come from the program context; the rules for mappings, structs, arrays and strings come from the pointer templates in the resources.

Part of the ethdebug post appendix, with ethdebug in depth and Step through a transaction.

The contract

Every scene below shows one contract, Scores. A player calls record(points): the contract adds the points and a streak bonus (points × streak, at most 100) to the caller's Player in players, adds 1 to the streak, appends the points gained to history, and adds to total and rounds. setMotto sets a string. The five state variables, players to rounds, are what the scenes show. Alice, anvil's first account, sends every transaction.

Scores.sol — the contract ( lines) 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract Scores {
    struct Player {
        uint64 score;
        uint32 streak;
        bool active;
    }

    mapping(address => Player) public players;
    uint256[] public history;
    string public motto;
    uint128 public total;
    uint64 public rounds;

    function bonus(uint256 points, uint256 streak)
        internal
        pure
        returns (uint256)
    {
        uint256 b = points * streak;
        if (b > 100) {
            b = 100;
        }
        return b;
    }

    function record(uint256 points) external {
        uint256 streak = players[msg.sender].streak;
        uint256 gained = points + bonus(points, streak);
        players[msg.sender].score = uint64(players[msg.sender].score + gained);
        players[msg.sender].streak = players[msg.sender].streak + 1;
        players[msg.sender].active = true;
        history.push(gained);
        total = uint128(total + gained);
        rounds = rounds + 1;
    }

    function setMotto(string calldata m) external {
        motto = m;
    }
}

Scene

total (a uint128) and rounds (a uint64) share one slot, slot 3. Click a byte in that word: its variable lights up in the tree. Click a variable: its bytes light up. Alice has called record(7) once, so total is 7 and rounds is 1.

Alice's Player is one entry in the mapping players. Its slot is keccak256(her address . slot 0), and score, streak and active share that one word. "How this was found" shows each step of solc's rule, from the mapping's slot to the bytes of streak.

Alice calls record(30) after record(7). Her streak was 1, so her bonus is 30 × 1 = 30: her score goes from 7 to 7 + 30 + 30 = 67, and her streak goes to 2. The slot stays the same; bytes inside it change. Before is after her first call, After after her second. Beside the lit word, a card shows it in the other state.

setMotto replaces a 9-byte motto with a 48-byte one. A string of 31 bytes or less lives in its slot, with 2 × its length in the last byte. A longer string keeps only 2 × its length + 1 in its slot, and its bytes move to keccak256(slot 2) and the slots after it. "How this was found" shows where the two rules part.

The same program, compiled by Vyper 0.4.3 (contracts/Scores.vy), after the same two record calls. Vyper emits no ethdebug, so the page has no rule from Vyper. Here it applies Solidity's rule (from solc's ethdebug output) to the Vyper contract's real storage: keccak256(key . slot 0) holds nothing, so the tree shows score 0, with no error. Vyper's own rule hashes the slot first, keccak256(slot 0 . key), and puts each member in its own slot: 67, 2 and 1 (true). Those three words are in the dump, and no value shown owns them; "How this was found" lists them.

What is not done yet

    
    
      
  • Mapping keys. A mapping does not list its keys. The page
      shows only keys read from the KECCAK256 inputs in a trace (Alice's
      address, from her record calls). Other entries may
      exist but are not shown.
    • 
      
  • Nested mappings. A mapping inside a struct or another
      mapping needs one template applied after another, with a key for
      each level. The page does not do that yet; Scores has none.
    • 
      
  • Vyper. Vyper emits no ethdebug. Its scene applies
      solc's rule to Vyper's storage, to show what a tool built on
      Solidity's rules reads; Vyper's own slots come from its
      trace.
    • 
      
  • Names in the templates. Template and type names such as
      t_mapping$_t_address_$… are solc's internal names.
      ethdebug does not require them.

Looking ahead: memory, with BUG
      preview: bugc from ethdebug/format main,
      not yet released

    
BUG is ethdebug's teaching language. Its compiler,
    bugc, is ethdebug's reference compiler. On main (PRs #328 and #343), bugc
    tells where each local variable is at each instruction, arrays and
    strings in memory included. The program below replaces one name in
    a list of three with a longer one. names is an array:
    its word holds an address, and at that address are the length and
    one word for each element. Each element word holds the address of a
    string: its length, then its bytes. The replace writes
    "grace hopper" at free memory and puts its address in
    the word of names[1]. The bytes of
    "grace" stay where they were, but no value points at
    them any more. Pick two points in the run, A and B, and show memory at one
    of them; cards beside the lit words show the other. As above, the
    byte ranges come from ethdebug's reference library
    (@ethdebug/pointers), which follows bugc's pointers against the
    memory at each point. Only the decoding into numbers and text is this
    page's own.
