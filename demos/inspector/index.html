Storage, by name

Pick a transaction. The page shows the contract's storage by Solidity name, before and after, and marks what changed. Click any value, changed or not, to see how it was found.

Decoded by ethdebug's reference library from solc's ethdebug pointer templates (solc PR #16990 preview build); base slots still come from solc's storageLayout today.

What is not done yet

    
    
      
  • Base slots. solc PR #16990 emits a template for each
      type, but not where each variable starts. The page takes each
      variable's first slot from solc's storageLayout output.
    • 
      
  • Value types. solc emits no template for a top-level
      value such as a uint256. For these, the page builds
      the region itself from storageLayout. Such values say so under
      "How this was found".
    • 
      
  • Mapping keys. A mapping does not list its keys. The page
      shows only the keys this transaction hashed (read from the
      KECCAK256 inputs in its trace). Other entries exist but are not
      shown.
    • 
      
  • Nested mappings. A mapping inside a struct or another
      mapping needs one template applied after another, with a key for
      each level. The page does not do that yet; these contracts have
      none.
    • 
      
  • Names in the templates. Template and type names such as
      t_mapping$_t_address_$… are solc's internal names.
      ethdebug does not require them.
    • 
    

  


  

    
Looking ahead: memory, with BUG
      preview: needs ethdebug/format PR #270,
      not yet merged

    
Work in progress: this section's example and
    design are still open.

    
BUG is ethdebug's teaching language. Its compiler,
    bugc, is ethdebug's reference compiler and emits the fullest
    ethdebug data today, including where each local variable lives in
    memory at each instruction. The program below finds gcd(1071, 462)
    = 21 by recursion. Each call gets its own frame in memory, with its
    own a and b; the frames stack up as the
    calls go deeper, and each frame's first word holds the frame of its
    caller, so the frames form a chain. Pick two points in the run, A
    and B, and show memory at one of them; cards beside the lit words
    show the other. As above, the byte ranges come from ethdebug's
    reference library (@ethdebug/pointers), which follows bugc's
    pointers against the memory at each point;
    soldb is not used. The decoding into values is this page's own.
