Storage, by name

Pick a transaction. The page shows the contract's storage by Solidity name, before and after, and marks what changed. Click any value, changed or not, to see how it was found.

Decoded by ethdebug's reference library from solc's ethdebug output (a preview build of Walnut's solc fork, walnuthq/solidity PR #10). Each variable's base slot, offset and type come from the program context; the rules for mappings, structs, arrays and strings come from the pointer templates in the resources.

Part of the ethdebug post appendix, with ethdebug in depth and Step through a transaction.

How this was found

The words in storage changed byte no value shown

Each slot holds one 32-byte word. The dump shows storage before or after the transaction (Before | After, above): the slots that hold the values on this page and the slots the transaction read or wrote, in address order, one word to a line; "⋯" marks a jump in address. Byte 0 is the most significant. Point at a value, a byte or an address to light it up. Beside each lit run, a card shows the same words in the other state, in the same columns.

What is not done yet

    
    
      
  • Mapping keys. A mapping does not list its keys. The page
      shows only the keys this transaction hashed (read from the
      KECCAK256 inputs in its trace). Other entries exist but are not
      shown.
    • 
      
  • Nested mappings. A mapping inside a struct or another
      mapping needs one template applied after another, with a key for
      each level. The page does not do that yet; these contracts have
      none.
    • 
      
  • Names in the templates. Template and type names such as
      t_mapping$_t_address_$… are solc's internal names.
      ethdebug does not require them.

Looking ahead: memory, with BUG
      preview: bugc from ethdebug/format main,
      not yet released

    
BUG is ethdebug's teaching language. Its compiler,
    bugc, is ethdebug's reference compiler. On main (PR #328), bugc
    tells where each local variable is at each instruction, arrays and
    strings in memory included. The program below finds the longest name
    in a list of three. names is an array: its word holds an
    address, and at that address are the length and one word for each
    element. Each element word holds the address of a string: its
    length, then its bytes. longest is a string, and its
    word holds the address of one of those strings, so the program copies
    no bytes. Pick two points in the run, A and B, and show memory at one
    of them; cards beside the lit words show the other. As above, the
    byte ranges come from ethdebug's reference library
    (@ethdebug/pointers), which follows bugc's pointers against the
    memory at each point. Only the decoding into numbers and text is this
    page's own.
