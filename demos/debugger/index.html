Step through a transaction

This page steps through a real transaction in this browser tab, offline, from saved files, and highlights the source range of each EVM step. A debugger, compiled for the browser, does the debugging; the page only displays what it reports. Use the step buttons, the keys, the slider, or click a source line to run to it.

The same debugger and the same page code step through a different language, because both compilers write ethdebug.

Shop.place: a saved trace of a real transaction (10 MB, 3,736 EVM steps), with solc's ethdebug output (Walnut's solc, walnuthq/solidity PR #10). soldb parses the trace (Trace.fromJson), reads solc's ethdebug (attachEthdebug), maps each step to its source (step(i)) and reads the contract's state (state(i)).

soldb, a Solidity debugger, stepping through a Fe contract, using only Fe's ethdebug output. Debugging by soldb (WebAssembly); the page adapts only the file layout, listed below.

Tally.Add{n: 4} (tally.fe): a loop, an internal call to weight and a branch, compiled by Fe 26.4.1 at -O 0. The transaction ran on a local anvil node; the page loads the node's saved responses with soldb's Trace.fromTransaction, then attachEthdebug and step(i), the same calls and the same viewer as the Solidity tab.

This tab runs ethdebug's reference implementation (@ethdebug/pointers, @ethdebug/evm and the trace reconstruction of @ethdebug/programs-react), not soldb. Local variables come from a preview build of BUG's compiler (ethdebug/format PR #270).

Weights (weights.bug): the code block calls weight four times; weight calls dbl and, from i = 2, tri, which calls itself. bugc marks each call with invoke and return contexts; the call stack comes from them. The same program, compiled at two optimization levels:

At level 0, bugc gives a local variable a pointer where its value is in memory. At level 2, it inlines dbl: those instructions carry transform: ["inline"] and keep the range of the call dbl(i); it emits no local variables.

    State from ethdebug alone: solc's pointers for storage, the deployed code for immutables; no storage layout.

    Variables in scope: the context's variables, each read through its pointer with dereference.

    A trace holds only the storage a transaction reads or writes, so a value shows as unknown until the transaction reads or writes it, and stays unknown if it never does.

    Values are decoded simply (uint, address), a stand-in for the format's planned interpretation layer.

    "over" and "out" use the depth of the call stack: "over" steps over a call or an inlined body, "out" runs to the caller. BUG has no grammar in Shiki: the code is coloured as Rust.

    The page computes these steps from two fields that soldb reports per step: the source span and the EVM call depth. "into" goes to the next new span; "over" to the next new span at the same or a lower depth; "out" to the first span after the depth drops. The EVM depth does not count internal function calls, and every step in these transactions is at depth 1, so "over" and "out" are disabled here. soldb's own step over and out (soldb-debugger) follow internal calls; its WebAssembly build does not expose them yet.

    What the page adapts (file layout only):

    • program: Fe's file holds two programs in a Fe-specific programs list; the page passes the runtime one (environment: "call").
    • sources: Fe lists its sources without their text. The page supplies it: tally.fe, and 7 standard-library files (builtin-core:/…, builtin-std:/…) copied from the Fe repository at tag v26.4.1. Their blake3 hashes match the ones in Fe's file.
    • metadata: Fe's whole file, unchanged. soldb reads the source ids and paths from its compilation; it needs no types or pointers, so none are added. name is the program's contract name.

    Display only: Fe has no grammar in Shiki, so the code is coloured as Rust. soldb reports byte offsets; the page converts them to string positions to draw the span (one std file has non-ASCII text). File names are shown without their directory. soldb reports no function names for Fe (its function detection targets Solidity) and no variables (Fe emits none).
