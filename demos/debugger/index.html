Step through a transaction

This page steps through real transactions in this browser tab, offline, from saved files. At each EVM step, it highlights the source range. A debugger engine, compiled for the browser, does the debugging. Each tab names its engine. The page only shows what the engine reports.

    Inlining

    soldb and this page step through Solidity and Fe with the same code. Both compilers write ethdebug.

    Shop.place: a saved trace of a real transaction (4.4 MB, 3,736 EVM steps). The ethdebug output comes from Walnut's solc (walnuthq/solidity PR #10). soldb parses the trace (Trace.fromJson) and reads the ethdebug (attachEthdebug). Then it maps each step to its source (step(i)) and reads the contract's state (state(i)).

    soldb, a Solidity debugger, steps through a Fe contract. It uses only Fe's ethdebug output. The page changes only the file layout (see the list below).

    Tally.Add{n: 4} (tally.fe) has a loop, an internal call to weight and a branch. Fe 26.4.1 compiled it at -O 0. The transaction ran on a local anvil node. The page loads the node's saved responses with soldb's Trace.fromTransaction, then calls attachEthdebug and step(i), as on the Solidity tab.

    This tab runs ethdebug's reference implementation, not soldb: @ethdebug/pointers, @ethdebug/evm and the trace reconstruction from @ethdebug/programs-react. The local variables come from bugc, BUG's compiler, on ethdebug/format main. Only the decoding of values is a stand-in, for the format's planned interpretation layer.

    Scores (scores.bug) scores three rounds. Each round writes its score to one element of the memory array recent (recent[i - 1] = s) and adds it to a total in the packed storage struct stats. score calls sq and sumTo, which calls itself. Look for: the call stack (up to five frames, from bugc's invoke and return contexts); recent as it fills, one element per round, read through its pointer (length, then each element); at -O2, the inlined sq and the folded local bonus. The tab has the same program at two optimization levels.

    At both levels, bugc gives a local variable a pointer where its value is in memory. Where a local has no location (its value is not stored yet, or the optimizer folded it), bugc lists it by type only: the format cannot yet say "the value is this expression" (ethdebug/format#291). At -O0, bonus is in memory. At -O2, the optimizer folds it into the sum, so it is listed by type only. At -O2, bugc also inlines sq. The inlined instructions carry transform: ["inline"] and keep the source range of the call sq(k). The local x of the inlined sq is marked "inline". It is listed from the step after the inlined call starts to the step of the instruction that returns from it; the next step lists the caller's variables again. In the inlined body, the storage variables stay listed. The pointer for last, a mapping, names only its base slot, so the page shows no entries.

    "over" and "out" use the call stack depth. "over" steps over a call or an inlined body. "out" runs to the caller. Shiki has no BUG grammar, so the code is coloured as Rust.

    The page computes each step from two fields that soldb reports: the source span and the EVM call depth. "into" goes to the next new span. "over" goes to the next new span at the same or a lower depth. "out" goes to the first span after the depth drops. The EVM depth does not count internal calls. Every step in these transactions is at depth 1, so "over" and "out" are off here. soldb's own step over and out (soldb-debugger) follow internal calls. Its WebAssembly build does not expose them yet.

    What the page changes (file layout only):

    • program: Fe's file holds two programs in a Fe-specific programs list. The page passes the runtime one (environment: "call").
    • sources: Fe lists its sources without their text. The page supplies the text: tally.fe, and 7 standard-library files (builtin-core:/…, builtin-std:/…) copied from the Fe repository at tag v26.4.1. Their blake3 hashes match the ones in Fe's file.
    • metadata: Fe's whole file, unchanged. soldb reads the source ids and paths from its compilation. soldb needs no types or pointers, so the page adds none. name is the program's contract name.

    Display only: Shiki has no Fe grammar, so the code is coloured as Rust. soldb reports byte offsets. The page converts them to string positions to draw the span, because one std file has non-ASCII text. File names show without their directory. soldb reports no function names for Fe, because its function detection targets Solidity. It reports no variables, because Fe emits none.
